LEADERSHIP DEMO · 3 MIN

Foundry + Windows 365
Computer-Use Agent

An end-to-end agent that operates a real Windows desktop — what it takes to build today, and where native integration removes the tax.

THE QUESTION

Not "can a customer build this" — how hard is it?

"We already know a customer can build an end-to-end computer-use agent on Foundry and Windows 365 — that's not in question. What we wanted to understand is how easy or hard that actually is today, and where Microsoft has a real opportunity to close the gap with native integration."
THE SCENARIO

One instruction. A real desktop. A human watching.

A Foundry-hosted agent opens a browser on a real Windows 365 Cloud PC, reads an invoice visually off the screen the way a person would, and writes a structured summary into Notepad — with a live, authenticated viewer link a human can watch or take over at any time.

WHAT IT TOOK · PART 1
0:25 – 1:10

Identity was the biggest piece of engineering

"A hosted Foundry agent can't call Windows 365 with its own credentials — we had to build a three-hop token exchange. The blueprint credential becomes an assertion, that gets exchanged for an agent-identity token, and that gets exchanged again for a scoped agent-user token — that last one is the only thing W365 actually accepts."
"And identity wasn't just tokens. We also had to create a dedicated W365 agent-user, license it, and assign it to a Cloud PC pool — separate from the agent identity itself. Three distinct identities, wired together, before a single token gets exchanged."
WHAT IT TOOK · PART 2

Three identities, one token chain

sequenceDiagram participant Setup as One-time identity setup participant Blueprint as Blueprint (Entra app) participant AgentId as Agent identity participant AgentUser as W365 agent-user Setup->>Blueprint: Register blueprint + credential Setup->>AgentId: Create dedicated agent identity Setup->>AgentUser: Create, license, assign to Cloud PC pool Note over Blueprint,AgentUser: All three provisioned by hand today participant Runtime as Foundry hosted agent participant Entra as Microsoft Entra ID participant MCP as Agent 365 W365 MCP Runtime->>Entra: T1 = blueprint assertion Runtime->>Entra: T1 to T2 (agent-identity token) Runtime->>Entra: T1 + T2 + agent-user to T3 (scoped token) Runtime->>MCP: Bearer T3 on every call MCP-->>Runtime: Live tool catalog + desktop actions

MCP wrapper

Connects to Agent 365's W365 tools, attaches the token to every call, and pulls the live tool catalog each session — nothing hardcoded.

Session lifecycle

Ownership + idempotency key before start. A valid screen-share URL is the readiness signal. Ambiguous outcomes are unresolved, never success. Always cleaned up.

Honest caveat

Wanted fully secretless, managed-identity end to end. One hop hit an Entra limitation — added a client-secret fallback just for that step. Stopgap, not the design we want.

THE ASK

Make the plumbing a platform guarantee

"If Windows 365 becomes a first-class Foundry tool — with Foundry brokering that token exchange and handling agent-user provisioning automatically, the way it already does for other MCP connections — most of that identity setup disappears. What's left is the business logic and the session-safety guarantees, which we'd keep either way.

It works today. It's just more identity plumbing than a customer should have to own — and that's a solvable platform gap."
